\section{Knowledge Graph Extension Implementation}
\label{chap:kg}

This section explains how the implemented pipeline publishes its relational evidence as a knowledge graph. The operational pipeline stores its results in SQLite because shell and Python functions can update relational tables directly during execution. The knowledge-graph layer has a different purpose: it converts the same evidence into connected RDF statements so that platforms, resources, notebooks, runs, executions, reproducibility results, and classifications can be queried together.

The implementation does not manually write RDF triples by hand. Instead, it follows a repeatable publication route. The working SQLite database is exported into a defined set of CSV files. These CSV files are mapped into RDF through YARRRML and RML mappings. Morph-KGC materialises the RDF fragments, RDFLib combines them with the ontology extension, and SPARQL tests check whether the generated graph contains the expected entities and relationships.

The main flow of the knowledge-graph implementation is therefore: working SQLite database $\rightarrow$ CSV export $\rightarrow$ YARRRML/RML mappings $\rightarrow$ RDF fragments $\rightarrow$ combined graph $\rightarrow$ SPARQL validation.

\subsection{Relationship to the FAIR Jupyter Knowledge Graph}

The implementation builds on the existing FAIR Jupyter knowledge graph rather than replacing it. FAIR Jupyter provides the semantic baseline for notebook reproducibility. It already contains the REPRODUCE-ME ontology, mapping files, and a Morph-KGC-based materialisation workflow. Its original data model focuses on publications, authors, GitHub repositories, notebooks, code features, requirements, executions, and reproducibility results \cite{samuel2024fairjupyter}.

The contribution of this thesis is a second operational data view produced by the cross-platform pipeline. This view comes from the working SQLite database created during pipeline execution. It describes GitHub and Codeberg repositories, Zenodo archived records, normalized metadata, processing runs, notebook executions, output-comparison results, and notebook classifications. These elements are not written as a separate unrelated graph. They are published under the same Notebook FAIR namespace and connected through an ontology extension.

The implementation keeps the original FAIR Jupyter files available for comparison. The baseline ontology file remains unchanged, while the new terms are placed in a separate extension file. This separation makes the thesis contribution visible. It also avoids mixing local platform-specific additions directly into the upstream ontology.

The graph builder therefore does not download a finished online graph and append new text to it. It reads the current pipeline data, applies the extension mappings, loads the ontology extension, and creates a new materialised graph. This makes the output repeatable: when the working database changes, the graph can be rebuilt from the same source rules instead of edited manually.

\subsection{Relational Data Export}

The first implementation step is relational export. The script \texttt{export\_pipeline\_csv.py} acts as the bridge between the SQLite database and the RDF mapping workflow. It reads the working database from \texttt{data/output/db/db.sqlite} and writes CSV files into \texttt{kg/fairjupyter/pipeline\_data/}.

The database connection is opened in read-only mode. This is important because knowledge-graph construction should publish pipeline evidence, not modify it. At this stage, the database is treated as the source of truth. The exporter only selects and transforms rows into CSV form.

The exporter uses seven named SQL queries. Each query corresponds to one evidence area of the pipeline: resources, metadata, notebooks, runs, executions, reproducibility metrics, and classifications. The queries select columns in a fixed order instead of using \texttt{SELECT *}. This makes the CSV headers stable, which is necessary because the mapping files depend on predictable column names.

\subsection{Ontology Extension and Resource Model}

The ontology extension defines the additional concepts needed to represent the cross-platform pipeline. It uses the Notebook FAIR namespace and imports the existing REPRODUCE-ME ontology. Where possible, the extension reuses established vocabularies: PROV-O for entities, activities, and agents; DOAP for Git repositories; and Dublin Core for descriptive metadata \cite{prov2013}.

The central resource class is \texttt{RepositoryResource}. This is a neutral parent class for any external source processed by the pipeline. GitHub repositories, Codeberg repositories, and Zenodo records can all be treated as repository resources in the broad sense that they provide notebook-containing material to the pipeline.

However, the ontology also keeps the platform difference visible. \texttt{GitRepositoryResource} represents resources that are real Git repositories. GitHub and Codeberg use this class. \texttt{ArchivedResearchRecord} represents non-Git archived records, such as Zenodo records. These two classes are kept separate because a Zenodo record does not become a Git repository just because its downloaded archive is processed as a local folder.

Figure~\ref{fig:kg-resource-classes} shows the resource classes in the ontology extension.

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{figures/chapter5/kg_resource_classes.png}
\caption{Resource classes in the ontology extension.}
\label{fig:kg-resource-classes}
\end{figure}

\texttt{RepositoryPlatform} is modelled as a PROV agent. The ontology declares GitHub, Codeberg, and Zenodo as platform individuals. Each resource is connected to exactly its hosting platform through \texttt{hostedOnPlatform}. This relationship allows a query to group resources by platform while still preserving their resource type.

The ontology also represents notebooks and processing activities. \texttt{NotebookResource} represents the registered notebook identity. It does not embed the full JSON content of the notebook. The relationship between a resource and its notebooks is represented using \texttt{containsNotebook} and the inverse relationship \texttt{isNotebookOf}.

Processing is represented with PROV activities. \texttt{RepositoryRun} represents one pipeline attempt for a resource. \texttt{NotebookExecution} represents the execution of one notebook during a run. \texttt{ReproducibilityResult} represents the measured comparison result linked to a notebook execution. This placement is important because the reproducibility score belongs to a specific execution result, not permanently to a repository.

Notebook classification is also represented as an activity. \texttt{Notebook\-Classification\-Activity} links a classification result to the notebook that was classified. This is necessary because the same notebook can be classified several times with different rule versions, AI models, prompts, thresholds, or human review decisions.

Datatype properties attach concrete values from the pipeline. Resources receive identifiers and file counts. Notebooks receive paths and language values. Runs and executions receive statuses, durations, and error information. Reproducibility results receive identical, different, nondeterministic, and total cell counts plus the reproducibility score. Classification activities receive rule and AI labels, confidence values, model information, agreement status, review flag, provisional category, final category, and warning.

Descriptive metadata uses standard terms where possible. Dublin Core provides properties for title, description, creator, licence, subject, identifier, created date, and modified date. The custom property \texttt{metadataFetchedAt} is used for the pipeline's local observation time. This separates metadata from the external resource from metadata about the pipeline's processing activity.

\subsection{YARRRML and RML Mapping Design}

After the ontology defines the model, mapping files define how CSV rows become RDF statements. The readable mapping source is written as seven \texttt{pipeline\_*.yaml} files. These files use YARRRML because it provides a compact syntax for describing CSV sources, subject templates, and predicate-object rules \cite{heyvaert2018yarrrml}.

The YARRRML files are not executed directly by Morph-KGC. The script \texttt{compile\ub pipeline\ub mappings.py} converts them into RML Turtle files using the pinned YARRRML parser package \cite{rmlspec}. The RML files are the executable mappings used during materialisation.

Figure~\ref{fig:mapping-compilation-flow} shows the mapping compilation flow.

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{figures/chapter5/mapping_compilation_flow.png}
\caption{Mapping compilation flow.}
\label{fig:mapping-compilation-flow}
\end{figure}

Stable subject templates are the most important part of the mapping design. A repository always receives an IRI based on its database ID. Notebooks, runs, executions, results, and classifications use their table name and database ID. Because the same identifier pattern is used across mappings, data from different CSV files can connect to the same RDF resource.

For example, the repository mapping creates a repository IRI from the repository ID. The metadata mapping uses the same repository IRI instead of creating a separate metadata object. This means title, authors, licence, DOI, and dates enrich the existing repository resource. They do not become disconnected metadata nodes.

The mappings also write inverse relationships where useful. A notebook is linked to its repository, and the repository is linked back to the notebook. A run is linked to its repository, and the repository is linked back to the run. Executions, results, and classifications follow the same pattern. These inverse links make SPARQL queries shorter and make structural tests easier because expected relationships can be counted directly.

Typed values are handled in the mappings. Counts use integer datatypes. Scores and durations use decimal datatypes. URLs and RDF classes are emitted as IRIs. Labels, statuses, messages, and category names remain literals. Empty CSV fields are left empty instead of being converted into invented values.

The compiler also supports a check mode. In check mode, the readable YARRRML files are compiled into a temporary location and compared with the committed RML files. If they differ, the build fails. This prevents a situation where the readable mapping was changed but the executable mapping was not updated. The build also requires exactly seven pipeline RML files, so a partial graph cannot be created unnoticed.

\subsection{Knowledge Graph Materialisation}

Materialisation is controlled by \texttt{build\_pipeline\_kg.py}. This script runs the complete graph-building process. Before creating RDF, it checks that Morph-KGC can be imported, that all seven mapping files exist, that the ontology extension can be parsed as RDF/XML, and that each mapping can be parsed as Turtle. These checks catch syntax or dependency problems before a long conversion starts.

Unless the user explicitly skips export, the builder first calls the CSV exporter. This ensures that the CSV files match the current working database. It then prepares output folders under \texttt{data/output/kg/}. These folders store Morph-KGC configuration files, logs, split graph fragments, the combined graph, and the build summary.

Each mapping is executed separately. For every RML mapping, the builder writes one Morph-KGC configuration file and produces one N-Triples fragment. Running the mappings separately has two advantages. First, each CSV dataset produces its own RDF fragment, so problems can be traced to a specific mapping. Second, the build summary can record triple counts and timing per mapping.

If Morph-KGC fails for one mapping, the builder reports the mapping name and log path instead of silently continuing with an incomplete graph. This is important because a graph that is missing one fragment could still parse as RDF but would not represent the full pipeline evidence.

After each fragment is produced, RDFLib parses it and counts its triples. Parsing confirms that the output is valid RDF. The count helps identify unexpected empty fragments or unusually large changes. The mapping duration is also recorded so later builds can be compared.

When all fragments are valid, the builder combines them. It loads the ontology extension and all RDF fragments into one RDFLib graph. Because RDFLib treats the graph as a set of triples, duplicate statements are stored only once. The combined graph is then serialized as \texttt{notebookfair-pipeline.nt}.

The build summary records the UTC build time, source database path, ontology path, combined graph path, total unique triple count, CSV row counts, fragment outputs, fragment triple counts, and mapping durations. These values connect the final RDF graph to the relational snapshot from which it was created.

The complete graph build can be started through the wrapper script \texttt{kg/}\allowbreak\texttt{fairjupyter/}\allowbreak\texttt{run\ub fairjupyter\ub kg.sh}. The wrapper resolves the project root, selects the correct Python environment, and passes the working database and output directory to the builder. This provides one repeatable command for rebuilding the graph.

Generated graph files can be deleted and recreated from the database, ontology, and mappings. This is preferable to editing N-Triples manually because every RDF statement has a documented source column and mapping rule. If new classifications or executions are added to the database, the graph is updated by rerunning the same build process.

\subsection{Representation of Notebook Classifications in RDF}

Notebook classification is included in the semantic publication route through the seventh mapping. Each stored classification row becomes a \texttt{Notebook\-Classification\-Activity}. The subject IRI contains the classification row ID, and the activity points to the notebook that was classified.

This representation preserves the method-specific results instead of publishing only one final category. The rule-based decision is represented separately from the AI-based decision. The reconciliation result is also represented. This means the graph can show whether the rule method and AI method agreed, disagreed, had low confidence, or required human review.

\subsection{SPARQL Competency Questions and Structural Validation}

After materialisation, the generated graph must be checked. The implementation does this with SPARQL competency questions and structural validation. The goal is not only to prove that the RDF file parses. The goal is to show that the graph actually contains the relationships required by the thesis.

Seven SPARQL files express the main questions that the graph must answer. They cover platform counts, metadata values, the path from repository to notebook execution and score, run statuses, average reproducibility score per platform, Zenodo archived records with DOI values, and notebook classification categories.

The structural checks are stricter than parsing. Entity counts for repositories, notebooks, runs, executions, results, and classifications must match the corresponding CSV row counts. The graph must contain all three platform names. Zenodo resources must be typed as archived records and must not be typed as Git repositories. A Zenodo DOI must be present when the test expects it.

Relationship counts are also checked. Every exported notebook must have a repository link. Every run must link to a resource. Every execution must link to a run. Every metrics row must link to an execution result. Every exported classification must link to a notebook. These checks confirm that the graph is connected rather than only containing isolated resources.

\subsection{Resulting Knowledge Graph}

The confirmed reproducibility snapshot produced a materialised knowledge graph containing 222,048 unique triples including ontology statements. The source snapshot contained 5,244 repository resources, 27,274 notebooks, 116 repository runs, 444 notebook executions, 444 reproducibility-result rows, and three normalized metadata rows. Six of the seven mapping fragments contained data for this snapshot, while the classification mapping participates in the same build and contributes instance triples whenever classification rows are present. The combined graph count is not simply the sum of the fragment counts because ontology statements are loaded and duplicate triples are removed during graph union.

The stored SPARQL test summary reports that the required structural checks passed. It confirms platform groups, metadata resources, execution routes, run-status groups, reproducibility-score links, and Zenodo archived-record representation. This shows that the graph is not only syntactically valid RDF, but also follows the relationships defined by the ontology and mappings.

The final graph is useful in two forms. The N-Triples file can be loaded into RDF tools or triple stores. The SPARQL result CSV files provide compact evidence for inspection, testing, and demonstration. More importantly, the graph connects information that is separated across relational tables: platform, resource, notebook, run, execution, reproducibility result, and classification.

This completes the knowledge-graph extension implementation. The pipeline first creates evidence in SQLite, then exports it through stable CSV contracts, maps it through versioned YARRRML/RML rules, materialises it as RDF, validates it with SPARQL, and records a build summary. The result is a traceable semantic output that can be rebuilt whenever the working database changes.
