\section{Notebook Classification Implementation}
\label{chap:classification}

This section explains how notebook classification is implemented inside the pipeline. The purpose of this part is different from notebook execution. Execution checks whether a notebook can run and whether its outputs can be reproduced. Classification describes what kind of notebook is being processed. This distinction is important because notebooks with different purposes may fail for different reasons. A tutorial, a visualization notebook, and a machine-learning notebook may all require different libraries, data files, and execution conditions.

The classification component is implemented as a separate Python package under \texttt{analysis/notebook\_classification/}. It is called after notebooks have been discovered and registered by the main pipeline. At that point, the notebook files exist locally and their database identities are known. Classification does not need the notebook to execute successfully, so it can run before dependency installation and notebook execution. This allows the system to keep a purpose category even for notebooks that later fail during the reproducibility route.

The implemented classification route has five main steps. First, the notebook is read and converted into a bounded evidence object. Second, a rule-based classifier can assign a category from transparent signals. Third, an AI-based classifier can receive the same bounded evidence and independently assign a category. Neither method is fixed as mandatory: by default both run, but either can be switched off on its own. Disabling both at the same time is rejected before any notebook is read, because at least one method must produce a decision. Fourth, whichever decisions are available are reconciled into an agreement status, review flag, and optional provisional category. Finally, the complete result is stored in the working database so it can be inspected, reviewed, evaluated, and exported to the knowledge graph.

\subsection{Classification Objective and Taxonomy}
\label{sec:classification-taxonomy}

The classifier assigns one main purpose category to each notebook. The category describes what the notebook mainly does. It does not describe the scientific subject of the notebook, and it does not say whether the notebook executed successfully. For example, a notebook about biology and a notebook about finance can both belong to \texttt{data\_analysis} if their main purpose is to analyse data.

The taxonomy is defined once in \texttt{categories.py}. This shared definition is imported by the rule-based classifier, the AI-based classifier, command-line validation, database review functions, and evaluation scripts. Using one shared taxonomy prevents different parts of the implementation from accepting different labels. If a category is not part of the taxonomy, it is rejected before it is stored.

The implementation uses nine categories: \texttt{data\_preparation}, \texttt{data\_analysis}, \texttt{visualization}, \texttt{machine\_learning}, \texttt{simulation}, \texttt{tutorial}, \texttt{software\_development}, \texttt{mixed\_purpose}, and \texttt{uncertain}. The first seven categories describe common notebook purposes. The last two categories are used when the evidence does not support a clear single purpose. \texttt{mixed\_purpose} is used when several purposes are equally central. \texttt{uncertain} is used when the notebook contains too little useful evidence for a reliable decision.

\subsubsection*{Notebooks Serving Several Purposes}

A notebook that both prepares data and analyses it --- or that prepares, analyses, and plots --- is the common case rather than the exception, as the corpus studies discussed in Section~2.7 report \cite{rule2018,kery2018,psallidas2022datascience}. The taxonomy therefore does not assume a single purpose. It resolves multi-purpose notebooks through an explicit, deterministic rule rather than leaving the outcome to whichever category happens to score marginally higher.

Each classification produces a \emph{primary} category and a list of \emph{secondary} categories. The rule-based classifier accumulates a weighted score per category from the collected evidence and then applies three cases in order:

\begin{enumerate}[label=\textbf{Case \arabic*.},leftmargin=1.9cm,itemsep=0.3em,topsep=0.3em]
\item \textbf{Insufficient evidence.} If the highest score is below 2.0, the notebook is labelled \texttt{uncertain} with confidence 0 and no secondary categories. No category is asserted on weak evidence.
\item \textbf{One dominant purpose.} Otherwise the highest-scoring category becomes the primary label. Every other category scoring at least 2.0 \emph{and} at least 65\% of the top score is retained as a secondary category. A notebook that mainly analyses data but also plots it is therefore \texttt{data\_analysis} with \texttt{visualization} recorded as secondary --- the subordinate purpose is preserved, not discarded.
\item \textbf{No dominant purpose.} If the second-highest score is at least 3.0 \emph{and} at least 90\% of the top score, neither purpose dominates. The primary label becomes \texttt{mixed\_purpose}, and the two tied categories become its secondary categories. Confidence is computed from their combined score, so a notebook with two strong purposes is not penalised for being genuinely mixed.
\end{enumerate}

To answer the question directly: a notebook that performs data preparation and data analysis is labelled \texttt{data\_analysis} (with \texttt{data\_preparation} secondary) when the analysis evidence clearly dominates, and \texttt{mixed\_purpose} (with both recorded as secondary) when the two are within 10\% of each other. A notebook doing preparation, analysis, and visualization follows the same rule on its top two scores; the third purpose is retained as an additional secondary category whenever it clears the 65\% threshold. The AI-based classifier returns the same primary/secondary structure and is instructed to choose \texttt{mixed\_purpose} only when several purposes are equally central, so both methods express multiplicity identically and remain directly comparable.

Two consequences are worth stating. First, \texttt{mixed\_purpose} is a substantive finding about a notebook, not a failure of the classifier --- unlike \texttt{uncertain}, which records that the evidence was insufficient. The two are kept separate for exactly this reason. Second, because the secondary categories are stored alongside the primary one, the evaluation in Section~\ref{sec:eval-classification} can analyse notebooks either by their dominant purpose alone or by the full set of purposes they serve, without re-running the classifier.

\subsubsection*{Role in the Evaluation}

This taxonomy makes classification usable for later evaluation. Instead of comparing reproducibility only by platform, the system can also ask whether certain notebook purposes are more difficult to reproduce. For example, machine-learning notebooks may depend on larger libraries or external datasets, while tutorial notebooks may be simpler and more self-contained. The category is therefore an additional context variable for interpreting execution and comparison results, and it is used in Section~\ref{sec:eval-cross-platform} to check whether an apparent platform difference is in fact a difference in notebook composition.

\subsection{Notebook Evidence Collection}

Classification begins with evidence collection. The function \texttt{collect\_notebook} reads the notebook file with \texttt{nbformat} \cite{nbformat}. It does not execute notebook code. This is important because classification should not depend on a successful runtime environment. The classifier only uses information already stored inside the notebook file.

The collector separates the notebook into Markdown cells, code cells, raw cells, metadata, imports, outputs, and structural counts. Markdown cells provide information about the stated purpose of the notebook, section headings, explanations, and tutorial-style language. Code cells provide information about operations, libraries, model training, plotting, testing, data loading, and other computational behaviour. Notebook metadata provides kernel and language hints. Output summaries provide evidence about what the notebook produced, such as text output, plots, tables, or errors.

Python imports are extracted using the standard-library \texttt{ast} module. For example, \texttt{import pandas as pd} is reduced to \texttt{pandas}, and \texttt{from sklearn.model\_selection import train\_test\_split} is reduced to \texttt{sklearn}. This keeps the feature representation compact and focuses on top-level package signals. Before parsing, the collector removes syntax that is common in notebooks but not valid as normal Python, such as IPython magics, shell commands, and help syntax. If a cell cannot be parsed as Python, the collector skips import extraction for that cell instead of failing the whole notebook.

Stored outputs are represented only by type. A display or execution result keeps its MIME types, a stream keeps the stream name, and an error keeps its error name. For example, a PNG plot contributes the signal \texttt{image/png}, but the actual encoded image bytes are not sent to the classifiers. Long text outputs, large binary objects, and detailed traceback contents are also excluded. This keeps the classifier input small and avoids sending unnecessary or sensitive content to the AI prompt.

The collected evidence object has its own version number. The implementation also calculates a SHA-256 hash of the notebook content. This hash records which notebook version was classified. If the same path later contains changed content, the hash can show that the classification belongs to a different notebook version. This is important because the same filename may appear in several runs or may change over time.

At the end of this step, the notebook has been converted into a bounded and reproducible input representation. The next stages use this representation instead of reading the notebook independently in different ways.

\subsection{Rule-Based Classification}

The first automated method is the rule-based classifier. Its purpose is to provide a transparent and repeatable baseline. Every score comes from an observable signal such as an import, phrase, code pattern, or output type. This means a reviewer can inspect why a notebook received a certain rule-based category.

The rule classifier uses package imports as strong category signals. For example, \texttt{pandas} supports data preparation, \texttt{statsmodels} supports data analysis, \texttt{matplotlib} supports visualization, \texttt{sklearn} supports machine learning, \texttt{simpy} supports simulation, and \texttt{pytest} supports software development. Each recognized import contributes points to the category associated with it.

The rule classifier also searches Markdown and code text with regular expressions. These patterns cover both natural-language descriptions and concrete code operations. For example, phrases such as ``feature engineering'' and calls such as \texttt{fillna(} support data preparation. Phrases such as ``hypothesis test'' and calls such as \texttt{corr(} support data analysis. Words such as ``dashboard'' and calls such as \texttt{plt.} support visualization. Functions such as \texttt{train\_test\_split} or \texttt{.predict(} support machine learning.

Each matched text pattern contributes a defined score. Repeated matches are capped, so one repeated word cannot dominate the result. The implementation still records both the uncapped number of matches and the counted number of matches. This allows a reviewer to see whether a signal appeared across the notebook or was repeated many times in one place.

Image outputs provide an additional visualization signal. If the stored outputs contain image MIME types, the rules add visualization evidence. This matters because some notebooks store plots even when the plotting library is not clearly detected from imports.

After all signals are counted, the rule classifier compares the category scores. If the highest score is too low, the notebook is classified as \texttt{uncertain}. This prevents one weak signal from creating a strong category. If one category clearly leads, it becomes the primary category. Other categories may be kept as secondary categories when they also have substantial evidence.

The confidence score is calculated from two ideas: dominance and signal strength. Dominance measures how much of the total evidence supports the winning category. Signal strength reduces the confidence when the absolute amount of evidence is small. This means a category can win but still receive only moderate confidence if the notebook contains little classification evidence overall.

\texttt{mixed\_purpose} is handled more conservatively than ordinary secondary categories. It is used only when the two strongest purposes are both strong and very close to each other. This avoids forcing a notebook into one category when the implementation has evidence that two purposes are equally central.

The rule method returns a structured \texttt{ClassifierResult}, not only a label. The result contains the method name, primary category, secondary categories, confidence, reason, evidence strings, scores for all categories, detailed signal statistics, and rule version. The rule set is versioned, so if weights or patterns change later, older classification results remain interpretable.

For example, a notebook that imports \texttt{matplotlib}, calls \texttt{plt.plot}, contains a Markdown heading about visualization, and stores PNG outputs will normally receive strong visualization evidence. If it also imports \texttt{numpy}, some data-analysis evidence may also appear, but the complete score dictionary shows how much influence each category had. This makes the rule result auditable rather than opaque.

\subsection{AI-Based Classification}

The second automated method uses a local AI language model. The default configuration uses Ollama with the \texttt{gemma3:4b} model \cite{gemma3}. The model name, base URL, timeout, and other settings can be changed through command-line arguments or environment variables. This keeps the classification contract independent from one fixed provider.

The AI method is intentionally independent from the rule method. It receives the category definitions and the bounded notebook evidence, but it does not receive the rule score or rule category. If both methods later agree, the agreement therefore represents two different methods reaching the same decision, not the AI model copying the rule-based result.

The prompt begins with the classification task and the nine allowed categories. It then explains the decision rules: choose one main category, use \texttt{mixed\_purpose} only when several purposes are equally central, use \texttt{uncertain} when the evidence is too weak, treat confidence as a self-assessment rather than a calibrated probability, and cite short observable evidence.

The prompt also includes an instruction that notebook text and code are untrusted data. This is necessary because Markdown and code cells are copied from external notebooks. A notebook could contain text such as ``ignore previous instructions'' or other misleading content. The implementation treats this text as data for classification, not as instructions that control the system.

The model is required to return structured JSON. The schema contains a primary category, secondary categories, confidence value, reason, and evidence list. The category fields are restricted to the nine allowed taxonomy labels. The same schema is passed to Ollama through its \texttt{format} field \cite{ollamastructured}. The client still validates the response independently because a schema-constrained model output is helpful but should not be treated as a guarantee.

The input sent to the model is bounded. The implementation includes the notebook path, cell counts, kernel and language metadata, unique imports, selected Markdown, selected code, and at most 100 output summaries. Markdown and code are limited by character count. This prevents very large notebooks from producing unbounded prompts and avoids sending embedded binary outputs.

A valid AI response becomes a \texttt{ClassifierResult} with method \texttt{local\_llm}. The result stores the primary category, secondary categories, confidence, reason, evidence, model name, prompt version, and raw response. The prompt version is recorded so that future changes to the prompt can be distinguished from older classification attempts.

Several AI-related problems are handled safely. Network errors, non-success HTTP responses, missing message fields, invalid JSON, unknown category labels, and invalid confidence values are converted into a classifier error. The pipeline does not lose the notebook because of this. Instead, the hybrid controller records that the model was unavailable, keeps the rule-based result when one was requested, and marks the notebook for human review.

This design makes the AI method useful but controlled. It can interpret broader notebook context than simple rules, but it cannot introduce arbitrary labels or replace the structured classification contract.

\subsection{Hybrid Reconciliation Strategy}

The hybrid stage combines the rule-based result and the AI-based result. It does not simply choose one method as always correct. Instead, it compares the two outputs and records how they relate to each other.

The main function collects the notebook once, runs whichever methods are enabled, and passes both results to the reconciliation function. Rules and the AI model are each independently switchable: by default both run, a rule-only mode skips the AI model, and an AI-only mode skips the rules. Disabling both is rejected before any notebook is read, because at least one method must produce a decision. The default confidence threshold is 0.55. The reconciliation output contains an agreement status, a Boolean review flag, an optional warning, and an optional provisional category.

If the rule method and AI method confidently choose the same primary category, the result is marked as \texttt{AGREED}, and the shared category becomes the provisional classification. If they choose the same category but one confidence value is below the threshold, the result is marked as \texttt{AGREED\ub LOW\ub CONFIDENCE}. The shared category is still visible, but the row is sent to review.

If one method chooses a category as primary and the other includes it as secondary, the result is marked as \texttt{PARTIAL\_AGREEMENT}. This means both methods found related evidence, but they did not agree strongly enough on one main purpose. If both methods choose different confident primary categories, the result is marked as \texttt{CLASSIFIER\ub DISAGREEMENT}.

Low-confidence cases are also separated. The implementation can record whether only the rule result was weak, only the AI result was weak, or both were weak. If both methods return uncertain, the result becomes \texttt{BOTH\_UNCERTAIN}. This is treated differently from ordinary agreement because it means both methods lacked enough evidence, not that they confidently agreed on a meaningful purpose.

If the AI method is disabled, the result is marked as \texttt{LLM\ub NOT\ub REQUESTED}. If the AI request fails or returns invalid output, the result is marked as \texttt{LLM\ub UNAVAILABLE}. In both cases, the rule label can still be shown, but the row requires review because the second method did not provide a valid independent decision. The reverse case is handled symmetrically: if the rule-based classifier was disabled, the result is marked as \texttt{RULE\_NOT\_REQUESTED} and the AI label is shown instead, again with mandatory review. If neither method produced a usable result, for example because the rule classifier was disabled and the AI request also failed, the notebook still receives a stored row with no provisional category, so the missing evidence remains visible rather than silently dropped.

\subsection{Database Storage and Human Review}

After reconciliation, the result is stored in the working database. The classification table is connected to the registered notebook identity. This connection is made through the notebook ID when the implementation can resolve the local path to exactly one notebook row. If the path is ambiguous, the system avoids creating an incorrect database relation.

The table stores both automated methods separately, and either one may be empty when that method was not requested. It keeps the notebook path and hash, the rule category and confidence, the AI category and confidence, the model name, prompt version, agreement status, review flag, warning, provisional category, final category, reviewer information, timestamps, and the full JSON result. This means the database does not only contain the final category. It contains the evidence needed to understand how the category was produced.

A new classification attempt creates a new row. This is important because the same notebook may be classified again after the rule version, prompt version, model, or confidence threshold changes. Human review can be performed for one classification row or through a CSV review queue. The blind review queue hides the automated predictions so the reviewer can assign labels independently. It can also use a fixed random seed to create a reproducible sample. This makes the review process suitable for later evaluation rather than only manual correction.

When reviewed labels are applied, the implementation validates them against the same taxonomy. A valid review updates the selected classification row with the final category, reviewer name, note, and review time. The automated rule and AI answers remain unchanged. This separation prevents human labels from being confused with automated predictions.

\subsection{Command-Line Integration and Failure Handling}

The classification component can be called from the pipeline or directly from the command line. It accepts notebook files or directories. When a directory is supplied, notebooks are found recursively, resolved to absolute paths, and deduplicated while preserving order. Each notebook produces a complete JSON result. With a database argument, the same result is inserted into \texttt{notebook\_classifications}. With an output argument, the results are also written to a readable JSON file.

The command-line options make the experiment configuration explicit. The user can run classification in rule-only mode, in AI-only mode, or leave both enabled for the hybrid default; select the AI model; set the Ollama URL; choose a timeout; and change the confidence threshold. Selecting rule-only and AI-only together is rejected immediately, before any notebook is read, because the implementation always requires at least one classification method to run. These settings affect how the classification was produced, so they are part of the experiment context.

The implementation handles three main failure types. First, collection failures occur when a notebook cannot be read or parsed as a notebook file. These failures affect that file. Second, AI failures occur when the model cannot be reached or returns invalid output. These become \texttt{LLM\ub UNAVAILABLE}, while the rule result is retained for review when rules were requested. Third, uncertainty is treated as a normal classification state rather than an exception. A notebook with too little evidence can be stored as uncertain and counted during evaluation.

This behaviour is important for batch execution. A single difficult notebook should not stop the classification of all other notebooks. The implementation stores the problem, keeps the available evidence, and allows later stages or later resources to continue when possible.

This completes the notebook-classification implementation.
