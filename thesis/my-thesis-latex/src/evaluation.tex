\chapter{Evaluation}
\label{chap:evaluation}

This chapter reports what the system measured. It answers two different kinds of question, and it keeps them apart.

The first question is whether the software works as Chapter~\ref{chap:requirements} required. Do the connectors recognise and download resources correctly? Is metadata normalized without inventing values? Does the database keep the evidence? Does the knowledge graph build and answer its queries? This is called \emph{technical validation}.

The second question is what the measurements say about the notebooks themselves. Three questions are asked, in this order:

\begin{enumerate}[leftmargin=*]
\item \textbf{How reproducible are the notebooks, and does the hosting platform make a difference?} This is the main empirical result, and Section~\ref{sec:eval-cross-platform} reports it.
\item \textbf{How well does the notebook classification work?} The pipeline assigns a purpose to every notebook using two independent methods. Section~\ref{sec:eval-classification} measures how good those assignments actually are.
\item \textbf{How well does the knowledge-graph build work?} Section~\ref{sec:eval-kg} checks that the graph contains the same evidence as the database and can answer the questions it was designed for.
\end{enumerate}

These two kinds of question must be separated. Passing the technical tests does not prove any research result. Measuring a corpus with an untested tool does not give trustworthy numbers either. The technical validation is therefore reported first, and the empirical results follow.

\subsection{How the Corpus Was Selected}
\label{sec:eval-corpus}

The corpus was not selected randomly. It was built by searching each platform for each notebook category on purpose, for the following reason.

A random sample needs a list of everything that could be sampled. No comparable list exists for these three platforms. GitHub offers a search API that can filter by programming language. Codeberg's Forgejo instance offers only limited search. Zenodo restricts automated access to its web search paths, so candidates there had to be collected through its records API instead. A random sample would therefore have been possible for GitHub and impossible in the same form for the other two. The result would have been one real sample and two convenience samples presented as if they were equal.

Candidates were instead collected per platform and per category, covering the seven substantive categories of the taxonomy from Section~\ref{sec:classification-taxonomy}. The categories \texttt{mixed\ub purpose} and \texttt{uncertain} were not searched for, because the classifier assigns them as outcomes; they are not something a repository can be found by.

Every candidate was then opened and checked by hand for real \texttt{.ipynb} files. This step removed a surprising number of candidates: repositories that did not exist, pure Python libraries described as containing notebooks, and projects using Marimo notebooks, which are \texttt{.py} files rather than Jupyter notebooks. Candidates that passed this check were processed by the pipeline. Those that then failed remain in the corpus as recorded failures. They were not removed, because a failure is evidence too.

\subsection{How the Numbers Are Counted}
\label{sec:eval-counting}

The repositories in the corpus have very different sizes. The median repository contributed 3 notebooks, 104 of the 282 repositories with results contributed exactly one, and the largest contributed 260. Two rules follow from this, and they apply to every table in this chapter.

\paragraph{Each notebook counts once.} Where a notebook has more than one execution result, the newer one is used. ``Notebooks'' in this chapter therefore always means distinct notebooks, not execution attempts.

\paragraph{Averages are reported in three ways.} Because the sizes differ so much, the way an average is taken changes the answer. A short example shows why. Suppose a platform has two repositories: one with 100 notebooks that each score 0.1, and one with a single notebook that scores 0.9. Averaging over notebooks gives 0.11, because the large repository decides the result. Averaging over repositories gives 0.50, because each repository counts once. Neither number is wrong, but they answer different questions, so this chapter reports both, plus a third:

\begin{itemize}[leftmargin=*]
\item \textbf{Notebook average:} every executed notebook counts once. This describes a typical \emph{notebook}, and large repositories carry the most weight.
\item \textbf{Repository average:} every repository counts once, using the mean score of its own notebooks. This describes a typical \emph{repository}, and a repository with one notebook counts as much as one with fifty.
\item \textbf{Balanced average:} the same number of repositories, and the same number of notebooks, is taken from every category on every platform. This compares the platforms on equal footing, because no category and no repository can contribute more than any other.
\end{itemize}

Section~\ref{sec:eval-balanced} shows that the three do not agree on which platform ranks first, which is the reason all three are reported.

\section{Connector and Pipeline Validation}
\label{sec:eval-connectors}

\subsection{Recognising and Rejecting URLs}

FR1 requires that supported URLs are recognised and unsupported hosts rejected. Detection was tested with valid and invalid URLs for each platform. The tests covered repository URLs with and without a trailing \texttt{.git}, links pointing into a file tree (\texttt{/blob/} on GitHub and \texttt{/src/branch/} on Codeberg), Zenodo record URLs in both the \texttt{/record/} and \texttt{/records/} forms, and plain numeric record identifiers.

All supported forms produced the correct platform and the correct normalized identifier. A deliberately unsupported URL ended with the status \texttt{UNSUPPORTED\ub PLATFORM} and produced no metadata row. This shows two things: the URL was rejected, and it was rejected before any platform API was contacted.

The success rate is less interesting than the pattern of the failures, and that pattern answers part of RQ1. The failures fall into two groups.

The first group is \emph{acquisition failures}. These depend on the platform. \texttt{METADATA\ub FETCH\ub FAILED} can only happen on a Git forge. \texttt{ZENODO\ub DOWNLOAD\ub FAILED}, \texttt{INVALID\ub ZENODO\ub RECORD}, and every case of \texttt{NO\ub NOTEBOOKS} happened only on Zenodo.

The second group is \emph{processing failures}: \texttt{PYTHON\ub INSTALL\ub FAIL}, \texttt{ENV\ub RUN\ub FAIL}, and \texttt{TIMEOUT\ub ERROR}. They occurred on more than one platform, and their share does not follow the platform. The timeouts are a property of resource size rather than of the host: they affected the largest repositories, such as a GitHub repository of tutorial notebooks that needs hours to run, and the 1{,}116-notebook Zenodo record mentioned above.

This split is the practical meaning of platform independence. The platform decides whether a resource can be obtained at all. Once the files exist in a local folder, the platform no longer predicts what happens next.

Zenodo's lower success rate is explained almost entirely by this. Of its 25 unsuccessful resources, 21 (84.0\,\%) failed before a single notebook was executed, either because the files could not be downloaded or because the record contained no notebooks. Neither is a fault of the pipeline. A Zenodo record may quite legitimately contain only a PDF, a dataset, or a source archive; this happened nine times. A GitHub-only study would never observe this situation, because its inputs are repositories that were selected for containing notebooks in the first place.

\subsection{Checking the Non-Functional Requirements}

NFR1 requires that the source database stays unchanged. It was compared before and after every run and remained byte-identical; all writes went to the working copy in \texttt{data/output/db/}.

NFR5 requires that a failure does not stop the batch. Table~\ref{tab:run-status} demonstrates this directly: 37 resources ended in a failure state, and every later resource still completed. Each failed resource kept its status and message.

NFR4 requires that the generated files can be rebuilt. The entire CSV and RDF output was deleted and regenerated from the working database, the mappings, and the ontology. The result is reported in Section~\ref{sec:eval-kg}.

NFR2 and NFR3 are used by every cross-platform query in this chapter. Each of them groups resources of different origin using shared status and metric definitions, while still keeping the platform of each result visible.

\section{Metadata Integration}
\label{sec:eval-metadata}

\subsection{Was Anything Invented?}

FR4 requires that metadata from each platform is mapped into eight common fields without inventing values that the source did not provide. This was tested for each platform by comparing the stored row against the raw API response.

Two things were confirmed. Every stored value can be traced back to a field in the API response. Every field that the response did not contain is stored as empty, and not as a default value, a placeholder, or a value taken from somewhere else.

All 318 analysed resources have a metadata row, including those whose notebooks could not be executed. Metadata retrieval and notebook execution are therefore independent: a resource that fails to run still contributes evidence about its platform's metadata.

Three observations follow from this table, and together they answer RQ2.

\paragraph{The platforms separate completely on persistent identifiers.} Zenodo provides a DOI for 112 of its 114 records (98.2\,\%). GitHub and Codeberg provide none, for any of the 204 resources between them. This is not a weakness of the connectors. It is a structural property: a DOI is created when a record is deposited, and a Git forge does not deposit anything. The consequence matters for reproducibility. A notebook published only on a Git forge has no persistent identifier, so it cannot be cited or resolved reliably once the repository is renamed, moved, or deleted.

\paragraph{Licensing shows the same difference more sharply.} Zenodo records a licence for 96.5\,\% of records, because the deposit form asks for one. GitHub records one for 50.5\,\%, because about half of the sampled repositories have no licence file. Codeberg records one for none at all, and the reason is worth stating carefully. The Forgejo repository endpoint does not return a licence field, not even for repositories that clearly contain a licence file. The 0\,\% therefore describes the API, not the repositories.

This is what the no-invention rule from FR4 prevents. A normalizer that filled this field by guessing, for example by searching the cloned folder for a \texttt{LICENSE} file, would have produced a number that looks just like GitHub's 50.5\,\% but means something completely different. The empty value keeps the two cases distinguishable.

\paragraph{Descriptive fields are nearly complete everywhere, and keywords are the exception.} Title, authors, and the two dates are present for 98--100\,\% of resources on all three platforms, so an integrated view of the corpus is possible without gaps in its basic description. Keywords are the one descriptive field that is weak everywhere, between 41.7\,\% and 55.4\,\%. Keywords are optional on all three platforms, and roughly half of all authors do not supply them, regardless of where they publish.

Taken together, metadata differences are not a formatting problem. They are a real difference in what each platform knows about the objects it stores. The value of normalization is not that it removes this difference, but that it makes the difference measurable. A design that had filled the gaps would have reported almost complete metadata everywhere and would have shown nothing at all.

\subsection{Structural Checks}

The graph is checked against the database it came from. All checks passed.

The entity counts recovered from the graph match the exported row counts exactly: 345 repositories, 5{,}617 notebooks, 334 runs, 2{,}872 executions, 2{,}872 reproducibility results, and 4{,}695 classification activities. The relation counts match as well, which confirms that no link between a repository and a notebook, a run and an execution, an execution and a result, or a notebook and a classification was lost or duplicated during mapping.

Two further checks protect the distinction that the ontology extension exists for. Every Zenodo resource is typed as an \texttt{ArchivedResearchRecord}, and no Zenodo resource is typed as a \texttt{GitRepositoryResource}. A graph that mixed these two would still be structurally valid, while describing an archived deposit as a version-controlled repository.

A third check confirms that Zenodo DOIs appear in the graph as \texttt{dcterms:identifier} values. The persistent identifiers from Table~\ref{tab:metadata-completeness} therefore survive into the semantic layer instead of being lost on the way.

\subsection{Does the Graph Say the Same as the Database?}

The fifth query repeats the platform comparison directly from the graph. It returns 1{,}456 results with a mean score of 0.3787 for GitHub, 733 with 0.3482 for Zenodo, and 645 with 0.3669 for Codeberg. Running the equivalent SQL query over the database returns exactly the same counts and the same means to four decimal places.

This agreement is the practical proof that the graph represents the same evidence as the database, and not a distorted copy of it. It also illustrates how precise such a check has to be. The query walks the path platform $\rightarrow$ resource $\rightarrow$ run $\rightarrow$ execution $\rightarrow$ result, so it only sees results whose execution still has a run record. Thirty-eight results belong to executions from interrupted runs whose record was removed, and the query therefore does not count them. The graph is not wrong; the query has a stricter definition than the tables in Section~\ref{sec:eval-cross-platform}, which count notebooks directly. Comparing the two on the same definition is what makes the check meaningful.

\section{Cross-Platform Reproducibility Results}
\label{sec:eval-cross-platform}

This section reports the comparison that RQ4 asks for. In total, \textbf{2{,}291 notebooks} from 282 resources were executed and compared, covering \textbf{38{,}087 code cells}.

\subsection{Execution Outcomes}

Every executed notebook receives one of two statuses. \texttt{SUCCESS} means every code cell completed without raising an error. \texttt{SUCCESS\ub WITH\ub ERRORS} means the notebook ran to the end, but at least one cell raised an error. The second status is not a pipeline failure: the notebook was executed completely, and the errors are the notebook's own.

Two results stand out.

\paragraph{The level is low on every platform.} Fewer than two cells in five reproduce their stored output. Even the best platform fails to reproduce more than 60\,\% of its cells. The finding that notebook outputs largely do not survive re-execution~\cite{pimentel2019,samuel2024computational} is therefore not something specific to GitHub. \paragraph{The platform order reverses between the two measures.} Codeberg has the best clean-execution rate (45.3\,\%) but not the best reproducibility score. GitHub has the worst clean-execution rate (30.8\,\%) but the highest score in this table.

A notebook that runs is not the same as a notebook that reproduces. A study that reported only execution success would have reached a different conclusion about which platform performs better, which is why the outputs are compared cell by cell instead of recorded as a simple yes or no.

The differences between the three platforms are small, however: 0.378, 0.367, and 0.348 span only three percentage points of cells. Before reading anything into that order, it has to survive a change of counting rule, and Section~\ref{sec:eval-balanced} shows that it does not.

This explains why Codeberg can have the best execution rate and still not lead on score. Its distribution is the most polarised of the three: it has both the largest share of perfectly reproducing notebooks and the largest share of notebooks that reproduce nothing at all.

\section{How Well the Notebook Classification Works}
\label{sec:eval-classification}

The hybrid classifier was designed on the assumption that two independent automated methods are better than one. This section tests that assumption in two steps.

The first step asks how \emph{good} each method is: how often does it assign the category a human would have assigned? The second step asks how the two methods \emph{relate} to each other: where do they agree, and where do they diverge? Agreement between two methods is not evidence of correctness, so the quality question is asked first.

Every one of the 2{,}291 analysed notebooks carries a rule-based result, and all 2{,}291 also carry a result from the language model. Coverage is therefore complete, and no figure below is weakened by missing classifications.

\subsection{What Can and Cannot Be Measured}

No human-labelled set of notebooks exists for this corpus, so true accuracy cannot be reported. What does exist is the category assigned to each \emph{repository} when the corpus was curated, which was decided by reading the repository's own description.

That curated category is used here as a reference label. Its weakness is that it belongs to the repository, not to the individual notebook. A repository curated as \texttt{machine\ub learning} will usually contain some notebooks that only prepare data or draw plots, and those notebooks will be counted as errors even when the classifier describes them correctly. The figures below are therefore a \emph{lower bound} on classifier quality, not a measurement of it.

The reference set is the 1{,}970 notebooks whose repository category was curated by hand.

\subsection{Confidence Behaviour}

The two methods report confidence in very different ways. The mean rule-based confidence is 0.49; the mean model confidence is 0.94.

The rule-based confidence is calculated. It derives from the ratio of the winning category's score to the total score, damped when the absolute evidence is weak, so it falls when the evidence really is ambiguous. The model's confidence is self-reported, and it is high almost everywhere, including on notebooks the rule-based method found ambiguous and including, as Table~\ref{tab:classifier-quality} shows, on the many occasions when it is wrong.

A confidence value that does not distinguish easy cases from hard ones carries no usable information. This is the practical reason the hybrid controller routes decisions on the basis of \emph{agreement} between the methods rather than on the model's stated confidence.

\subsection{What the Hybrid Design Achieves}

The hybrid controller assigns a provisional category only when the evidence justifies it, and flags the rest for human review. Applied to the reference set, it committed to a category for 346 of 1{,}970 notebooks (17.6\,\%) and flagged 1{,}803 (91.5\,\%) for review.

Where it committed, it matched the curated category for 151 of 346 notebooks, or \textbf{43.6\,\%}. That is meaningfully better than the model alone (36.6\,\%) and far better than the rules alone (17.8\,\%), which means the reconciliation logic does select the more trustworthy cases. But it buys that improvement by deciding almost nothing: on more than eight notebooks in ten it defers to a human, and even on the cases it accepts it is still wrong more often than right.

The evidence therefore supports the design assumption only in a narrow sense, and refutes a stronger one.

The two methods are genuinely complementary, and this is not merely asserted but visible in the numbers. They have opposite strengths: the rule-based method is precise where imports and function calls are decisive and abstains when they are not, while the model is decisive everywhere and strongest exactly where the rules are weakest. The 193 tutorials recovered from the rule-based method's unclassified pile are the clearest single illustration, and the reconciliation behaves sensibly in ranking its own output by trustworthiness.

What the evidence does not support is using either method, or their combination, as a finished labelling system for individual notebooks. A macro F1 of 0.29 for the better of the two, and a hybrid that has to defer 91.5\,\% of decisions, describe a component that is useful for triage and not yet useful for measurement. This is why Section~\ref{sec:eval-category-effect} treats its own category table with caution, and why the balanced platform comparison deliberately uses the curated repository category instead of the classifier's output.

Two limits qualify these figures in the classifier's favour. The reference label is repo-level and therefore noisy, as Section~\ref{sec:eval-classification} explained, so the true quality is somewhat higher than 36.6\,\%. And the model used is a small one, chosen so that the whole corpus could be classified locally and repeatedly at no cost; a larger model would very likely score better. Neither limit changes the conclusion for this corpus, and Section~\ref{sec:future-classification} describes what a proper evaluation would require.

The generated part of the analysis can be repeated completely. Deleting all CSV and RDF output and running the build again produces the same graph and passes the same checks; this is how the numbers in Section~\ref{sec:eval-kg} were obtained. Every table in this chapter is produced by a script that reads the database, so the chapter can be regenerated after any correction to the data.

The download and execution part cannot be repeated exactly, and the reasons are built into the problem rather than being mistakes.

Repositories change after they are cloned, and this work did not record the commit hash that was used. This is a genuine gap, and it is listed in Section~\ref{sec:future-technical}. Package installation resolves against a live package index, so running the same pipeline months later installs different versions. Notebooks that download data depend on that data still being available.

Zenodo records are the exception. A published record version preserves its deposited files under a persistent identifier, although its metadata can still be updated and new files appear as a new version. The files are what matters here, and they held: when two notebooks had to be classified again, their record was downloaded a second time and both files matched their original checksums exactly. This is a real advantage of archival deposit, and this study can observe it directly only because it processed both kinds of platform.

\section{Answers to the Research Questions}
\label{sec:rq-answers}

\paragraph{RQ1: To what extent can a platform-independent reproducibility workflow support the analysis of computational notebooks across heterogeneous research platforms?}
To a large extent, and with a clear boundary. In total, 318 resources across three platforms were processed by one workflow, and 281 of them (88.4\,\%) reached execution, producing 2{,}291 compared notebooks. Platform-specific handling is limited to validation, metadata retrieval, and acquisition. After a local resource folder exists, no stage needed platform-specific behaviour, and the same code processed Git repositories and extracted archives in the same way. The boundary is real rather than nominal: 21 of Zenodo's 25 failures happened before it, and the failures after it follow resource size rather than platform. The main limitation lies at the same boundary. An archived record may contain no notebooks at all, which happened nine times, and this situation cannot arise for a repository that was selected because it contains notebooks.

\paragraph{RQ2: How does metadata heterogeneity across research platforms affect the integration and representation of computational notebooks and their reproducibility-related information?}
The differences are substantial, and integration is only meaningful with a strict rule against inventing values. Eight fields were normalized across three vocabularies for all 318 resources. The platforms separate completely on persistent identifiers, with Zenodo providing a DOI for 98.2\,\% of its records and both Git forges providing none, and on licensing, at 96.5\,\%, 50.5\,\%, and 0\,\%. The Codeberg figure describes its API rather than its repositories, and only a normalizer that refuses to guess preserves that distinction. Descriptive fields behave differently: title, authors, and dates are 98--100\,\% complete everywhere, so the platforms differ in what they \emph{guarantee} rather than in what they \emph{describe}. At the representation level, integration worked without losing these distinctions: 162{,}008 triples were produced, all structural checks passed, including the check that no archived record is described as a Git repository, and the graph reproduces the database's platform comparison to four decimal places.

\paragraph{RQ3: To what extent do rule-based and AI-based approaches agree when characterizing computational notebooks into reproducibility-relevant categories, and to what extent do the two approaches complement each other?}
They agree only slightly, they complement each other clearly, and neither is accurate enough to be relied on alone. The two methods chose the same category for 19.1\,\% of the 2{,}291 notebooks both classified, with Cohen's $\kappa = 0.11$, rising to 25.5\,\% and $\kappa = 0.14$ when the rule-based method committed to a substantive category. Measured against the curated repository category, the language model reaches 36.6\,\% accuracy and a macro F1 of 0.29, against 17.8\,\% and 0.15 for the rule-based method; a trivial classifier that always answers the majority category would reach 31.5\,\%. The complementarity is asymmetric and systematic rather than incidental: the rule-based method is precise where imports and function calls are decisive and abstains on 27.2\,\% of notebooks, whereas the model is decisive everywhere and strongest where the rules are weakest, recovering 193 tutorials from the rule-based method's unclassified pile. Their confidence behaviour differs in the same direction, since the calculated rule-based confidence distinguishes easy from hard cases while the model's self-reported confidence (mean 0.94) does not. The hybrid controller exploits this correctly, reaching 43.6\,\% agreement with the curated label on the 17.6\,\% of cases it accepts, but it defers the rest to a human. Combining the two is therefore justified as a triage mechanism and not as a measurement instrument, and the reference label used here is itself noisy, so these figures are a lower bound.

\paragraph{RQ4: To what extent do computational notebooks differ across platforms with respect to metadata completeness, execution outcomes, failure causes, and reproducibility-relevant categories?}
They differ measurably, but less than the raw numbers first suggest, and not all in the same direction. Metadata completeness is highest on Zenodo and lowest on Codeberg. Clean-execution rates run the other way, at 45.3\,\% for Codeberg, 34.5\,\% for Zenodo, and 30.8\,\% for GitHub. Output reproducibility depends on how it is counted, and this is the most important qualification of the whole chapter: counting every notebook once puts GitHub first at 0.378, while counting every repository once puts Codeberg first at 0.37 and GitHub third at 0.29. Only one comparison survives all three counting rules, namely that Codeberg repositories reproduce better than Zenodo records, with non-overlapping intervals of [0.32, 0.42] and [0.22, 0.31]. Missing dependencies are the largest single failure cause across the corpus at 20.9\,\%, and stay in a narrow band of 17.1\,\% to 25.8\,\% on every platform, although on GitHub code errors are slightly more frequent at 21.9\,\%. File errors concentrate on GitHub at 15.7\,\% and interactive-input errors on Zenodo. Notebook purpose affects reproducibility by about as much as the platform does, which is why the balanced design holds it fixed. Two qualifications limit these results: the samples were chosen on purpose rather than at random, and the assigned notebook categories come from a classifier of moderate quality. What can be stated without qualification is that low output reproducibility is not specific to GitHub, because it holds on all three platforms and under every counting rule.

\section{Summary}
\label{sec:eval-summary}

The technical requirements are met. Platform detection, validation, acquisition, normalization, evidence storage, and semantic publication all behave as Chapter~\ref{chap:requirements} specified. The knowledge graph builds to 162{,}008 triples, passes every structural check, answers all seven competency questions, and reproduces the database's own platform comparison exactly.

The empirical results support three claims, qualify one, and withhold one.

First, platform-independent processing works, and the boundary lies exactly at acquisition. Second, metadata differences between platforms are substantial, and normalization makes them measurable instead of hiding them. Third, output reproducibility is low on all three platforms: fewer than two code cells in five reproduce their stored output, whichever way the notebooks are counted.

The qualified claim concerns the platform comparison itself. The platforms do differ, but the ranking depends on whether notebooks or repositories are counted, and only the difference between Codeberg and Zenodo survives every counting rule. Using raw notebook counts alone would have reported a GitHub lead that the balanced design does not support, so each reported score names the counting rule it belongs to.

The claim that is withheld concerns classifier quality. Measured against the curated repository category, the language model reaches a macro F1 of 0.29 and the rule-based method 0.15. The two methods are demonstrably complementary, and the hybrid controller is right to route on agreement rather than on self-reported confidence, but a component that defers more than nine decisions in ten is a triage aid rather than a measurement instrument. Establishing what these methods can really do requires labels assigned by a person at notebook level, which was outside the scope of this work. Chapter~\ref{chap:future-work} explains what that would involve, and what else would be needed to strengthen the results reported here.
